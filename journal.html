**JOURNAL FOR CART 351**

WEEK 1: SEPT 14th Journal 1

This week in the class of CART 351, we reviewed HTML, CSS, JavaScript, and the DOM. As someone who has worked with some of these languages before, the lesson was a great refresher and allowed me to familiarize myself with the basics once more. However, I found it fascinating how JavaScript can be used in tandem with the DOM to create dynamic web pages. It was a great reminder that websites do not have to be as rigid as they might seem at first glance. We also reviewed how client-servers communicate via HTTP. It was interesting to learn more about the technical process behind how HTML, CSS, JavaScript, and images are sent from a server to a website and subsequently displayed on the user’s screen. I am looking forward to learning more about server-side programming in this class. It will be exciting to see how my existing knowledge of programming will come together with my creative expression.

WEEK 2: SEPT 21st Journal 2

This week was my first encounter with Python for the course, and it was at a good time, straight after we covered Python Foundations 1 in class, so I had a good enough understanding in my head to actually get why exercise 1 was testing what it was testing. The exercise I did was a collection of small, isolated puzzles like: fix an expression so that it evaluates to a particular number, flip a comparison operator, coax a variable into the right type, slice a string down to a single word. They were all easy enough on the surface, but I noticed that each one was trying to show a concept introduced in the lecture: operator precedence and floor division for Task 1, boolean comparisons for Task 2, type() and Python’s dynamic typing for Task 4, .find() and slicing for Tasks 6 and 10. Actually doing the exercise right after the reading was helpful as a kind of instant feedback loop: read a concept, and five minutes later prove to yourself you actually understood it by making a broken line of code produce the right output. The two I had to think the hardest about were the string slice (Task 10) and the double-condition logic (Task 13). For the first one, I kept making guesses about indices instead of actually counting characters in “Did the cat jump out the window yesterday?”, which is honestly a good reminder that Python’s zero indexing punishes guessing and rewards just counting properly. For Task 13, the fix wasn’t obvious until I slowed down and separately thought about each side of the "and", which I thought was a useful lesson in not skimming boolean expressions. That said, where this connected to something bigger was that I’m also using this exercise as the first real content for my course website, and I found that the user experience side of things came in at this point. My first instinct was to just link to the raw .py file on GitHub, but sitting with it for a bit I realized that’s a pretty unsatisfying experience for anyone visiting the site, you’d see code, not proof it works. So I went looking for a way to actually run Python in a static, GitHub pages hosted site, and found Pyodide, which is a full Python interpreter compiled to WebAssembly that runs clientside. After setting that up (with the help of AI) so that the exercise auto runs and prints its own terminal output right in the browser, just felt like an upgrade that wasn’t that big, but was meaningful and turned the exercise from just being able to see my code into “here’s my homework, and you can see it work.” For next week I’m looking forward to learning more about functions, loops, and lists, especially default/keyword arguments and list slicing, since slicing already gave me trouble on the strings and I suspect it’ll show up again.

WEEK 3: SEPT 28th Journal 3

This week’s class on dictionaries, URLs and web APIs helped a lot with the exercise. Part 2A reviewed lists, and Part 2B was my first time pulling live data from an API. Part 2A was about indexing, slicing and list methods. The main lesson was that a slice stops before the end index, so the second through fourth items needed start = 1 and finish = 4. Counting works better than guessing, same as last week’s string slice. I also noticed that .sort() and .append() change the list itself, so the order of the tasks mattered. And I lost time on Task 17 because the starter code said “carret”, not “carrots”. Part 2B is where the things clicked a bit more. A dictionary looks up values by key instead of index, and an API normally returns a list of dictionaries. That’s exactly what the Star Wars API gave me: each planet had keys like "name" and "diameter", so planet["name"] read like plain English. Reading the URL as scheme, host and path also made it less mysterious. Two problems came up. The numbers arrive as strings, and some are "unknown", so converting everything to int would crash. Then I used rich to build a table, and the same data became much easier to read with aligned columns and thousands separators. It was really exciting to see it work as intended when I got it all running. To show this on my site, I used Pyodide so visitors can press “Run” and see the output in their browser, since GitHub Pages can’t run Python itself. This part was extra and I am not proficient enough to do it by myself, so I had help from Claude. I added loading messages because the first run is slow. I suppose a lesson is that if code is working on my computer, it isn’t automatically usable for someone else.

Week 4: OCT 19th Journal 4

I learned a bit about this new thing Flask this week. I found out it's a light weight Python web framework. My Python scripts were making requests to a server last week, but this week they are acting as the server. The main thing here I found out is routing. Which means we can use the @app.route() decorator to tell the server which URL path should trigger a Python function. I found dynamic routes very interesting. For example, /user/. This means for all users, we can have one function which will display their profile. This must be how real sites work as there would be thousands of users, which I found exciting because I am getting closer to being able to set up a site for myself and fully understand it. The decorators makes sense after the quick tangent. I learned that the @ symbol means adding extra functionality to a function without having to change the function. So using @app.route will tell the server which URL to link to which page. The most useful thing was using Debug mode. If there is a small error such as trying to find the 100th letter in a short string, by default it will just say 'Internal Server Error'. However, I learned that using debug=True means that the browser will show us the full traceback and interactive console. This got me thinking about error messages and how it can make our lives much easier. The notes do mention to make sure you turn it off once deployed because it shows a lot. Using templates helped me see how everything fits together. i learned that instead of returning HTML as a string in Python, we can use templates. We can also use Jinja to insert data into the templates using {{variable}} and we can use {% for %} and {% if %} to loop through lists and dictionaries. This ties into last weeks lesson on APIs as often the data we get back is a list of dictionaries. It is interesting how the data comes from an API, gets processed in Python and displayed in a template. The logged in example showed me how personalised websites can become. It also helped me understand something on my own site. I wanted my Python exercises to display on my portfolio, however as GitHub Pages only displays static files I had to use Pyodide to run Python in the visitors browser. I suppose know I know that another option could have been to use Flask. This would mean Python runs on the server and the completed pages get sent to the visitor. I now understand why I had to use a workaround on my site. I am interested to see what I could create if I had a server!
